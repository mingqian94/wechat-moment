# 朋友圈发布助手

多账号朋友圈自动化发布工具。Python 实现，Mac 开发，Windows 运行。

---

## 快速开始（Mac 开发环境）

```bash
# 1. 建虚拟环境
/opt/homebrew/bin/python3.12 -m venv .venv
source .venv/bin/activate

# 2. 装依赖
pip install -r requirements.txt

# 3. 配置私钥（开发用）
echo "WM_PRIVATE_KEY=你的私钥" > .env

# 4. 生成测试注册码
python src/auth.py

# 5. 启动
python src/main.py
```

Mac 上会用 mock 微信窗口，GUI 和调度逻辑可以完整测试，图像识别和真实发布需要 Windows 验证。

## 使用流程

### 首次使用

```
Step 1: 用多开工具把所有微信账号登好
Step 2: 启动程序，自动检测微信窗口并显示头像（templates/ 自带默认按钮模板，一般不用管）
Step 3: 进入主界面，开始使用
```

### 日常使用

```
Step 1: 确认微信已全部登录（多开工具已开好）
Step 2: 启动程序，自动识别已登录的微信账号（显示头像）
Step 3: 点「+ 添加任务」，右侧面板展开
        → 选素材：
          · 选文件夹：自动读取文件夹内所有图片/视频，按文件名排序
          · 选文件：手动多选文件，按选择顺序排列
        → 勾选要发布的账号（可多选，每个账号生成一条任务）
        → 填文案（支持粘贴 emoji）
        → 填发布时段（如 09:00 — 12:00，至少 10 分钟）
        → 确定后程序自动随机分配各账号的发布时间
Step 4: 任务列表中可查看每条任务的时间、账号、素材、状态
        → 双击或点「编辑」可修改文案和素材（时间不可改）
        → 点「删除」或右键删除单条任务
Step 5: 点「▶ 开始全部」，弹窗提示预计完成时间，确认后开始
        → 发布期间勿操作电脑（程序自动控制鼠标键盘）
Step 6: 如有失败任务，右键选「重发此任务」
```

### 素材命名规范

- 文件夹内文件按文件名排序决定发布顺序，命名格式：`01.jpg`、`02.jpg` … `09.jpg`（补零）
- 每条任务最多 9 个文件（微信限制，超出自动截取前 9 个）
- 支持格式：jpg / jpeg / png / bmp / mp4 / mov

### 视频发布说明

- 视频和图片**不能混发**，请分别存放在不同文件夹
- 视频时长不能超过 30 秒（微信限制），程序会自动检测并提示
- 一次只能发布一个视频（微信限制），如文件夹内有多个视频只取第一个
- ⚠ **视频"发布成功"可能误报**：程序点发表后等 60 秒检测"视频未发送"横幅来判断结果，
  但风控拒发时该横幅有时 60 秒后才出现，程序会漏检、误报成功。发视频后**建议人工抽查
  一下朋友圈**确认真的发出去了。（彻底解决需"发布后回头巡检朋友圈"，暂未实现）

## 风险说明

1. **封号风险**：同一台电脑高频/多账号发布可能触发微信限制，本工具通过随机时间分配降低风险，但不保证零风险
2. **新设备登录限制（结构性风险，代码无法绕过）**：微信对"新设备"有 24-72 小时的朋友圈发布限制，期间发送显示"未发送"，这个限制是**按设备/登录会话算的，不是按账号整体算**——同一账号手机端能正常发，PC 端微信刚登录/被识别成新设备时可能单独被限制。多开工具登录的 PC 微信实例如果总是被判定成"新设备"，那不管自动化做得多像真人操作，刚登录的账号短期内大概率发不出去，这跟点击节奏、文案、图片内容都没关系。实测：换真实风景照、调整点击时机均未解决"未发送"，换手机发同账号反而成功，指向这是设备维度的限制。建议登录新设备后先正常用一段时间（聊天、刷朋友圈，别用脚本）再开始自动发布。
3. **版本兼容**：微信更新可能导致按钮位置/样式变化，需重新截图校准模板。新版微信（Qt51514QWindowIcon 类名）与传统 PC 版均已适配
4. **多开工具依赖**：本工具不处理微信多开，用户需自备多开工具
5. **授权安全**：注册码方案防随意扩散，不防专业破解。本地测试可设置 `WM_DEBUG=1` 跳过验证

## 调研：发送失败可能的成因排查（联网调研，非微信官方确认）

微信风控的具体实现是黑盒，没有官方文档，下面是结合实测现象 + 通用反作弊/反 RPA 技术原理整理的分析，供排查"未发送"问题时参考，不是确凿结论。

**已基本排除/影响很小的因素**：
- 新设备 24-72 小时限制——账号过了这个时间窗后仍失败的话，不是这条原因
- 发布频率——`scheduler.py` 的 `ACCOUNT_LEVELS` 间隔（25-360 分钟）比网传"10 分钟一条"的下限宽松很多
- 文案内容——`caption_pool.py` 用的是日常生活感悟类文案，没有敏感词，风险低

**仍然存在、且代码层面没法完全解决的因素**：
- **同设备/同 IP 短时间内多开多个账号**：这本身就是风控重点关注的信号，跟单条朋友圈的点击操作像不像人没关系，是账号关联维度的风险，跟"自动化做得多逼真"是两件事。
- **合成输入 vs 真实硬件输入的系统级差异**：`pyautogui` 在 Windows 上底层走 `SendInput`/`mouse_event`，这类"合成输入"在 OS 层和鼠标驱动产生的"原始输入（Raw Input）"是可区分的（比如低级鼠标钩子能读到 `LLMHF_INJECTED` 标记）。目前项目做的"鼠标轨迹随机化 + 操作间隔随机化"解决的是"动作像不像人"这个维度，解决不了"这个点击信号本身是不是合成的"这个更底层的维度。微信是否真的检测这一层不确定，但技术上可行，如果以后要进一步降低风险，需要类似 Interception 驱动级模拟方案，复杂度高，目前没做。
- **多账号同设备行为同步**：如果多个账号都是同一份脚本驱动，即使各自的点击间隔分别随机化过，服务端做账号关联分析时仍可能发现"这几个账号的行为统计分布高度相似"，这条目前没有针对性缓解措施。

## 技术备注：窗口截图

`window_manager.py` / `image_recognition.py` 截取微信窗口时优先用 `PrintWindow(PW_RENDERFULLCONTENT)`，桌面DC BitBlt 仅作降级方案。原因：新版微信左侧导航栏（含头像）是硬件加速/分层渲染的子区域，桌面DC BitBlt 截不到，会透出背后桌面像素，但又不会让整张图全黑，容易被误判为"截图成功"。如果以后要改回 BitBlt 优先，要先确认目标区域不是硬件加速渲染的。

## 开发注意事项：不要擅自调整用户的微信窗口

调试截图模板/头像定位时，**不要用 `SetWindowPos` 等 API 强行移动或缩放用户正在用的真实微信窗口**——曾经为了校准模板坐标反复改过用户微信窗口的大小和位置（从隐藏到任务栏的状态拖出来，又调成好几种尺寸），事后才被指出这是不该做的。

正确做法：
- 让用户自己截图按钮位置（参考下面"模板图截图说明"），或在用户已经手动打开/调整好的窗口上只读截图，不要反向控制窗口几何状态
- 确实需要现场校准时，先说明要做什么并取得明确同意，而不是默默操作后再汇报
- 如果窗口已经被改动过，操作结束后要主动还原（这次复原方式：`SetWindowPos(hwnd, 0, -16000, -16000, 157, 25, 0)`，即微信自身"隐藏到任务栏"时使用的离屏坐标）

头像在新版微信窗口内是**固定像素偏移**（相对窗口左上角约 x=40, y=90, 边长 62），不随窗口缩放变化（导航栏宽度固定），不要改回按窗口比例计算。

## 技术备注：朋友圈发布弹窗是独立窗口

点击主窗口左侧的"朋友圈"图标后，弹出的不是主窗口内的一个子区域/页面，而是一个**全新的独立顶层窗口**（不同 hwnd，标题含"朋友圈"）。相机图标、发表按钮都在这个新窗口里。

`publisher.py` 的 `execute_publish` 流程里，点完 `moments_btn` 之后必须调用 `window_manager.find_moments_window(主窗口hwnd)` 拿到这个新窗口的 hwnd，后续找相机图标、发表按钮都要用新 hwnd 截图/激活，不能继续用主窗口的 hwnd——之前就是因为一直用主窗口 hwnd 截图，导致相机图标永远匹配不到（截到的是主窗口自己的内容，不是弹窗内容）。

已通过真实发布流程验证：朋友圈→相机→选图→粘贴文案→点发表，全部步骤都能正确定位和点击。

## 技术备注：选完图片/视频后别太快点发表

选完图片/视频到点"发表"之间，微信需要时间在本地完成处理（缩略图生成/转码）才能真正开始上传，这个过程跟网络快慢无关，纯本地耗时。如果点发表点早了，按钮本身点击是对的，但会出现"照片未发送"/"视频未发送"——不是点错了，是点快了。

`execute_publish` 选完素材后会等一段时间再去点发表：图片按张数算（每张 1.5 秒，单张最少等 5 秒），视频按文件大小算（每 MB 1.5 秒，最少 8 秒最多 30 秒）。如果实测还是出现"未发送"，先加大这个等待时间，不要去改点击逻辑或坐标。

## 技术备注：测试发布别用"测试发布xxx"当文案

联调测试时如果反复用同一个账号、同一张图、"测试发布1"/"测试发布2"这种文案密集发朋友圈，很容易被微信风控判定为异常账号，导致"照片未发送"（这是限流，不是 bug，也不是网络问题，参考上面"窗口截图"之后那几节的踩坑记录）。

测试/调试发布时用 `src/caption_pool.py` 的 `random_caption()` 随机取一条自然语气的"生活感悟"短句当文案，别再手写"测试发布xxx"：

```python
from caption_pool import random_caption
task = {"caption": random_caption(), ...}
```

这个文案池是本地写死的一批短句，不接云端 AI 接口（项目本身不依赖云端），只用于开发联调，不是给真实用户日常发布用的文案生成器。

同时记得控制测试频率——`scheduler.py` 的养号策略（每日/每小时上限、最小间隔）就是用来防止这类风控触发的，联调时如果跳过 scheduler 直接连续调 `execute_publish`，等于把这层保护关掉了，别短时间内对同一账号测太多次。

**更新**：后来确认"未发送"看起来很随机的真正原因，大概率是下面"风险说明"里第2条的"新设备登录限制"，不是单纯的发布频率问题——同一账号手机端能正常发，PC 端微信反复失败，换内容、调时机都没用，换设备发就成功了。频率控制依然该做（这是基本的防风控卫生习惯），但如果 PC 端微信是刚登录的，光控制频率解决不了"未发送"，得等设备限制期过了。

## 技术备注：鼠标轨迹和等待时间都要随机，不要用整数秒

之前点击是 `pyautogui.click(x, y)` 直接瞬移到目标点再点，等待用的也是 `time.sleep(0.3)` 这种固定整数/半整数秒——这两者都是规律性很强的机器特征，容易被行为分析识别。已经改成：

- **鼠标轨迹**：[image_recognition.py](src/image_recognition.py) 的 `_human_move_click()` 会在起点和目标点之间插 1-3 个随机偏移的中间点，每段用 ease 曲线 + 随机时长移动过去，不再是直线瞬移。`find_and_click` 内部已经切换成调用它，不需要在别处手动改点击方式。
- **等待时间**：所有模拟人操作节奏的 `time.sleep()` 都改成 `random.uniform(下界, 上界)`，且上下界本身也尽量避免整数（比如 `0.85~2.95` 而不是 `1.0~3.0`）。选完图片/视频到点确认之间专门加了 2-5 秒随机停顿（模拟人选完文件会看一眼再确认，不会填完路径立刻回车）。

不要改回固定数值或整数范围；调度循环里那种纯内部轮询用的 `time.sleep(1)`（比如 `scheduler.py` 等待任务时间到、等待上一个任务完成）不算这个范畴，那是检查间隔，不是模拟人的动作节奏，没必要随机化。

## 开发环境踩坑：本机预装软件会干扰自动化测试

在本机（非用户最终部署机器）联调测试时，遇到过腾讯电脑管家弹出一个置顶窗口、刚好盖在微信窗口原本的屏幕位置，导致截图/找按钮短暂失效（表现跟找不到按钮一样，容易误判成代码 bug）。这类安全/管理软件的弹窗经常以较高权限运行，脚本里用 `PostMessage(WM_CLOSE)` 关不掉（拒绝访问），只能手动关掉。

排查"找不到按钮"类失败时，先看一眼 `错误截图/` 目录里实际截到的是不是真的微信界面，不是的话先处理干扰窗口，不要急着改坐标或模板。

## 技术备注：点发表 ≠ 发布成功，必须验证"未发送"才能关弹窗

之前 `execute_publish` 点完发表按钮、等几秒就直接返回成功——这是错的。点击成功只代表按钮点中了，图片/视频是否真的传上去，还要看点完之后会不会跳出"照片未发送"/"视频未发送"的提示，这个判定本身需要时间（不是瞬间出现），关弹窗、判断成功都不能在这一步之前做。

现在的做法：点完发表后，轮询检测"未发送"提示是否出现（统一轮询 20 秒；之前图片 8 秒、视频 12 秒，多账号风控导致失败信号延迟可能超过 8 秒，改为 20 秒统一兜底）。同时同步扫主微信窗口（`main_hwnd`），因为"照片未发送"有时出现在主窗口朋友圈 feed 里而非发表弹窗里。检测到就是失败，返回失败原因，**弹窗保留不关**，方便看错误截图排查；检测不到才算成功，这时才调用 `window_manager.close_window(moments_hwnd)` 关掉朋友圈弹窗（发 `WM_CLOSE`），避免残留弹窗挡住下一个账号的操作。

检测"未发送"踩过一个坑：一开始想用提示前面那个小图标（蓝色/红色圆圈+感叹号）做模板，结果发现**这个图标会变色/动画**（同一条记录第一次截图是蓝紫色，几分钟后再截变成红色），图标模板匹配不稳定。改成匹配"未发送"这三个字（`templates/send_failed_text.png`）——"照片未发送"和"视频未发送"前两个字不同但都是2个字，"未发送"位置完全一致，纯文字渲染不会变，匹配稳定（实测同一张截图前后两次匹配度从忽高忽低变成稳定 0.999+）。以后如果要改这块判断逻辑，不要回头用图标模板。

另外实测发现"未发送"不一定是永久终态——同一条失败记录在编辑框里直接重新点发表，立刻又失败，说明短时间内重试没用（跟"新设备登录限制"是按时间窗口算的这个解释吻合，不是单次随机失败）。按你的要求，只要轮询窗口内出现过"未发送"就判定为失败，不去等更长时间或重试确认，这是产品策略选择，不是检测不准。

## 技术备注：微信失去焦点后会把自己设成不可见（不是最小化）

`activate_window` 原来只处理"窗口被最小化"（`IsIconic` 为真）这一种情况，调 `ShowWindow(SW_RESTORE)` 恢复。实测发现微信失去焦点后还有另一种隐藏方式：`IsIconic` 是假，但 `IsWindowVisible` 也是假——既不是最小化，但就是看不见，截图/找按钮全部失败，表现跟"找不到窗口"一样容易误判成别的问题。

现在 `activate_window` 多加了一步：如果 `IsWindowVisible` 是假，调 `ShowWindow(SW_SHOW)` 让它先变回可见，再走原来的激活流程。这个判断和"是否最小化"是两件独立的事，不要合并成一个 if。

## 技术备注：测试视频用真实 H.264 编码

`gen_test_assets.py` 原来用 OpenCV 默认的 `mp4v` fourcc 生成测试视频，实际编码出来是老式 MPEG-4 Part 2（FMP4），不是手机录像那种 H.264——微信的视频上传/转码管线可能根本不认这种编码，导致视频发布测试失败时没法判断是自动化逻辑的问题还是素材本身的问题。

现在改用 `imageio-ffmpeg`（自带 ffmpeg 二进制，不用系统装 ffmpeg）编码成真正的 H.264 + yuv420p，跟真实视频更接近。重新生成测试视频需要先 `pip install imageio imageio-ffmpeg`（只是这个生成脚本要装，不是项目运行依赖，没加进 `requirements.txt`）。`test_video/test_clip.mp4` 已经用新方式重新生成好，5秒、1088x1088（ffmpeg 要求宽高是16的倍数，1080 自动垫到1088）、H.264，可以直接拿去测视频发布。

## 修复：头像截图颜色不对（BGR/RGB 通道反了）

`window_manager.py` 的 `_capture_window()` 截图时，肤色会显示成蓝色，背景色也明显不对——实际是 BGR 通道和 RGB 通道搞反了。

根因：`GetBitmapBits` 返回的像素数据是 **BGRA** 顺序，但两处都直接 `Image.fromarray(img[..., :3], 'RGB')` 或 `Image.fromarray(img, 'RGBA').convert('RGB')`——这只是给 PIL 贴了个"这是 RGB/RGBA"的标签，并不会真的把字节顺序倒过来，所以 R 通道和 B 通道的值被对调着显示了。其中桌面DC BitBlt 那个分支甚至已经写了注释"GetBitmapBits 返回 BGRA，需转成 RGB"，但代码根本没做转换，注释和实现不一致，没人发现。

修法：把第三维通道顺序显式反过来再交给 PIL，`img[:, :, [2, 1, 0]]`（取 R=原索引2、G=原索引1、B=原索引0），而不是直接贴标签。两个方法（PrintWindow 和桌面DC BitBlt）都改了。

顺手删掉了 `_capture_window_screenshot()`——同样的 bug，而且全项目没有任何地方调用它，是死代码。

`image_recognition.py` 里截图按钮用的是 `cv2.cvtColor(..., cv2.COLOR_BGRA2BGR)`，那是对的（OpenCV 内部本来就用 BGR 顺序，模板图也是用同样方式截的，自洽），这次没改它，颜色错误只出现在头像截图这条路径上。

## 修复：添加任务确认后，面板没有自动关掉

`_confirm_add()` 成功添加任务后本来就调用了 `self._hide_add_panel()`，但实际点"确定"面板纹丝不动——bug 不在调用时机，在判断条件上：

```python
def _hide_add_panel(self):
    if self.add_panel in self.main_paned.panes():   # 这个条件永远是 False
        self.main_paned.remove(self.add_panel)
```

`PanedWindow.panes()` 返回的不是字符串列表，是一组 `_tkinter.Tcl_Obj`。拿 `tk.Frame` 对象去 `in` 这组 `Tcl_Obj`，Python 用的是对象相等（`__eq__`），不是路径名比较，所以永远匹配不上——`_toggle_add_panel()` 里也是同样的写法，同样的坑，意味着再次点"+ 添加任务"想收起面板时也一直没生效，只是因为一直没人测过"已展开状态下再点一次"这条路径。

验证过 `str(p) == str(widget)` 才是两边都转成 Tcl 路径名字符串、能正确匹配的写法（`Tcl_Obj` 本身不支持和 `str` 直接 `==`，但两边都转成 `str` 后内容一致）。改成统一的 `_is_add_panel_shown()` 方法，两处调用都换成它：

```python
def _is_add_panel_shown(self) -> bool:
    return any(str(p) == str(self.add_panel) for p in self.main_paned.panes())
```

实测：填完素材/账号/文案/时间，点"确定"，面板立即收起、任务出现在左边列表里；再点"+ 添加任务"重新展开、再点一次收起，都正常了。

## 评估："开始全部" / "全部停止" 两个按钮要不要留

结论：建议都保留，目前没有更好的替代方案。

- **"开始全部"**：这个程序的执行模型是"今天所有任务一次性丢给 `Scheduler`，按各自的 `scheduled_time` 依次轮询触发"（见 `scheduler.py` 的 `Scheduler._run()`），不存在"只发某一条"的概念——单条重发走的是右键菜单"重发此任务"，是另一条路径（`_retry_selected` → `on_retry`），跟"开始全部"不冲突。也就是说"开始全部"不是"全部"和"部分"两个选项里的一个，它就是唯一的启动入口，去掉它整个调度就没法启动了，按钮名字里的"全部"容易让人误以为还有个"开始部分"的选项，但功能上没法去掉。
- **"全部停止"**：`Scheduler.stop()` 只是把 `_running` 置为 `False`，调度循环下一次检查就会退出（`_wait_until`/`_run` 里都在轮询这个标志）。这是测试时反复用到的手动急停开关——比如发现文案有问题、电脑要挪去做别的事、连续失败但还没到自动停止的 3 次阈值——目前没有任何自动机制能替代这个人工急停，建议保留。

如果觉得"开始全部"这个名字别扭，可以考虑改成"开始发布"/"开始执行"去掉"全部"两个字（纯文案改动，不影响逻辑），但功能本身两个按钮都是必需的，不建议删。

## 修复：文件路径正斜杠导致"文件名无效"

2026-06-30 调度触发时发现：`_select_images_dialog` 把路径写入 Windows 文件对话框后，对话框弹出"文件名无效"，文件始终选不上，导致任务失败（报"找不到发表按钮"——因为文件对话框没关、挡住了朋友圈弹窗，10 秒后点发表超时）。

- `_select_images_dialog`：写入前先 `norm = [p.replace("/", "\\") for p in image_paths]`
- `_select_video_dialog`：`SendMessageW` 参数改为 `video_path.replace("/", "\\")`

验证：用正斜杠路径直接调 `execute_publish()`，文件对话框正常接受路径（无"文件名无效"弹窗），选图步骤通过，后续失败是微信风控（"照片未发送"），不是路径问题。

- 运行时用 `GetDpiForSystem()` 读取当前机器实际 DPI，算出 `_base_scale = 当前DPI / 192`

这样只要新机器的按钮视觉比例没有魔改（正常情况都没有），换机器不需要重新截图，程序自己算出对应缩放比去匹配。

同时修复了打包相关的路径 bug：`sys._MEIPASS`（只读资源，模板图）和 `Path(sys.executable).parent`（可写文件，`activation.dat`/`logs/`）在 `image_recognition.py`/`auth.py`/`logger.py` 里分别处理，之前用 `__file__` 在打包后的 exe 里会指向错误路径。

## 排查：文案框 emoji 显示黑方块——不是输入丢失，是 Tk 渲染限制

2026-07-01 用户反馈添加任务面板的文案框"输入不进去"。用剪贴板校验实际输入内容（`pyperclip.paste()` 读回 `ctrl+A`/`ctrl+C` 选中的文本），emoji 的 Unicode 码点（如 😴=`0x1f634`、🐶=`0x1f436`）完全没丢，字符是**正常存进去的**。

根因是 Tkinter 在 Windows 上不支持渲染彩色 emoji 字形（COLR/CPAL 彩色字体表），不管指定什么字体，emoji 在编辑框里只会显示成黑色方块——这是 Tk 本身的老限制（当前用的 Tcl/Tk 8.6.15 也一样），不是这个项目代码的 bug，没有低成本修复方案。发布时走剪贴板复制粘贴（`_paste_caption`），粘贴进微信后由微信自己的渲染引擎显示，emoji 能正常显示——**实际发布效果不受影响**，只是编辑框里显示难看。

处理方式：在文案框下方加了一行灰色提示文字，而不是试图修复 Tk 底层限制。

## 排查中：反复出现"找不到朋友圈按钮"

2026-07-01："手动发送"实测确认过是真实调用 `execute_publish()` 操作微信（不是本地状态假动作），但两个账号连续 5 次都精确失败在同一步——Step 2 找 `moments_btn.png`。之前判断过是偶发，现在多次复现，是真实存在的系统性问题。

排查过程：
1. 独立脚本直接调用识别逻辑现测两个账号，`moments_btn.png` 匹配分数 0.98 / 0.9997（远超 0.80 阈值）——说明**空闲、已稳定渲染状态下模板和识别逻辑没问题**
2. 但失败瞬间的错误截图里，左侧导航栏（朋友圈图标所在区域）是空白的，窗口其余部分（聊天列表、消息区）渲染正常

当前假设：微信从"失焦隐藏"状态被重新唤起后，侧边导航栏（大概率是单独 GPU 合成的图层）重绘滞后于窗口其余部分；`PrintWindow` 有一定概率截到还没重绘完成的旧画面，且这张旧画面可能被短时缓存，6 秒内反复截图截到的都是同一张——重试次数再多也没用，因为问题不是"运气不好没截中"，是"一直读到同一张坏图"。

这只是有依据的假设，先按假设加了两处加固（`src/publisher.py`）：
- 新增 `_nudge_repaint()`：激活窗口后用鼠标划过窗口内部触发一次真实重绘，代替单纯延时等待
- `moments_btn.png` 的查找超时从 6 秒延长到 10 秒
- `image_recognition.py` 新增 `save_match_view()`，把识别逻辑真正用来比对的那张图（而非普通 `ImageGrab` 截图）单独存一份，命名带 `_matchview` 后缀

结果：加固后 `moments_btn` 超时仍然复现，但这次拿到了 `_matchview` 截图——发现 `save_match_view()` 用的 `cv2.imwrite()` 在 Windows 上遇到中文路径（错误截图目录名就是中文）会**静默失败**，返回 `False` 但不报错，导致诊断图片实际根本没写出来。改用 `cv2.imencode()` 编码后走普通文件句柄写，绕开这个坑，才真正拿到证据。

拿到证据后真相大白：两次 `_matchview` 截图内容都不是当前实时画面——一次是几小时前的另一个聊天窗口，一次是程序刚启动那一刻（19:16）的"文件传输助手"画面且侧边栏完全空白，跟当时的真实时间（22:43/22:44）对不上。而同一时刻用普通 `ImageGrab` 截的诊断图两次都是**实时、正确**的内容。结论：**`PrintWindow(PW_RENDERFULLCONTENT)` 对这个微信窗口不可靠，会返回冻结的旧缓存帧，不会随时间刷新**，跟侧边栏重绘滞后无关——不管重试多少次、等多久都没用，因为读到的一直是同一张坏图。

`PrintWindow` 之所以最初被引入，是为了应对"窗口被遮挡时 BitBlt 桌面截图会透出背后桌面"的问题；但 `execute_publish` 截图前已经 `activate_window()` 把目标窗口真正置顶，遮挡风险已经不大。修复（`image_recognition.py` 的 `_grab_region`）：改为**桌面截图（ImageGrab）优先**，只有当桌面截图疑似空白/被遮挡（`std <= 5`）时才退回 `PrintWindow` 兜底。

2026-07-02 实测：改为桌面截图优先后，`moments_btn` **仍然失败**（手动发送×2 + 自动调度共 3 次，全部失败在同一步）。但这轮拿到了新证据，之前的"结论"需要修正：

1. **昨天那张"旧缓存帧" matchview 里侧边栏图标其实是可见的**，离线跑匹配得分 0.9884（远超 0.80 阈值）——失败瞬间保存下来的画面明明匹配得上，实时匹配却失败了，这个矛盾之前被忽略了。说明"PrintWindow 陈旧缓存"可能不是（至少不是唯一的）失败原因。
2. **今天的 matchview 里截到的是另一个应用的窗口**（测试时开着的 Claude 桌面客户端）盖在微信侧边栏位置——桌面截图是所见即所得，任何窗口压在微信上面都会被截进匹配图。`activate_window()` 成功只代表拿到**键盘焦点**，不代表**视觉上没被挡**：普通窗口的 Z 序不一定让开，置顶悬浮窗（截图工具、网速悬浮球这类）更是完全不受 SetForegroundWindow 影响。
3. 还发现一个测试方法论问题：真机 exe 是 DPI-aware 进程（启动时调了 `SetProcessDpiAwareness(2)`），而之前用来验证"匹配分数 0.98/0.99"的诊断脚本是裸 python（非 DPI-aware），两者的窗口坐标处在不同缩放空间，之前那些"识别逻辑没问题"的离线验证结论说服力要打折。以后跑诊断脚本必须先设置同款 DPI 感知模式。

新的修复（2026-07-02，`window_manager.py` + `publisher.py`）：不再依赖"激活了就应该没被挡"的假设，改为**实测**：
- 新增 `get_occluder_title(hwnd)`：取微信左侧导航栏中部的一个屏幕点（36 逻辑像素 × DPI 缩放，图标列中心），用 `WindowFromPoint` + `GetAncestor(GA_ROOT)` 查这个点实际归属的顶层窗口——是微信自己返回 None，被挡则返回遮挡窗口的标题
- 新增 `raise_window(hwnd)`：短暂 `SetWindowPos(HWND_TOPMOST)` 再取消，把窗口硬拉到普通窗口最顶层（比 SetForegroundWindow 强硬）
- `execute_publish` Step 2 之前：检测遮挡 → 被挡就硬置顶重试（最多 3 次）→ 仍被挡则直接失败并在日志里**报出遮挡者的窗口标题**（"微信窗口被「XXX」遮挡"），不再让问题以"找不到朋友圈按钮"这种模糊面目出现
- `moments_btn` 匹配失败的报错信息追加窗口位置坐标，方便事后核对坐标空间

这个修复的效果还没实测验证。如果下次又失败，日志里要么出现遮挡者标题（定位到具体是谁挡的），要么排除遮挡因素后继续查别的方向。

**2026-07-02 晚间：真正的根因找到了，上面所有猜测都是干扰项。**

加上遮挡检测后再测：遮挡检测通过（导航栏区域确实归属微信窗口）、matchview 里侧边栏图标清晰可见，但实时匹配依然失败。把失败瞬间的 matchview 用**与 exe 完全相同的代码路径**（DPI-aware + 同款 SCALES + 同款阈值）离线重跑：**0.9997 分，完美命中**。同一张图、同一套匹配代码，离线能中、exe 实时不中——那唯一的区别只剩模板加载这一环。

检查 `_load_template()`：用的是 `cv2.imread()`。**`cv2.imread` 跟 `cv2.imwrite` 是同款坑：Windows 上遇到含中文的路径静默返回 None，不报错不抛异常。** 打包后模板路径是 `dist\朋友圈发布助手\_internal\templates\moments_btn.png`——**文件夹名"朋友圈发布助手"是中文**。每次加载模板都返回 None，`find_template` 直接返回找不到，10 秒重试循环里每一次都在做无用功。

这个结论把之前所有怪现象全部串起来了：
- **为什么 onefile 时代能发成功、切 onedir 后 100% 失败**：onefile 运行时解压到 `%TEMP%\_MEIxxxx`（纯英文路径），模板加载正常；onedir 的 `_MEIPASS` 就是 `_internal` 目录，路径含中文。失败恰好从切 onedir 那一刻开始，时间线完全吻合
- **为什么开发环境的诊断脚本永远复现不了**：仓库路径 `D:\mingqianRay\wechat-moment\templates\` 全英文，`imread` 一直正常
- **为什么错误截图看起来"按钮明明在"**：按钮确实在，截图和匹配算法都没问题，是模板侧为 None
- 之前的"PrintWindow 陈旧缓存""侧边栏重绘滞后""窗口遮挡"都是真实存在的现象（PrintWindow 确实截到过旧帧、Claude 窗口确实挡过右半边），但都不是匹配失败的原因——排查时被这些真现象带偏了方向

修复（`image_recognition.py` 的 `_load_template`）：`np.fromfile()`（Python 层面开文件，unicode 安全）读字节 + `cv2.imdecode()` 解码，替代 `cv2.imread`。已验证：同一张模板放到含中文的路径下，`imread` 返回 None，`fromfile+imdecode` 正常返回 (54, 70, 3)。

教训：**cv2 所有直接接文件路径的 API（imread/imwrite/VideoCapture 等）在 Windows 上都不能碰含非 ASCII 的路径**，一律走字节流（fromfile+imdecode / imencode+写文件句柄）。给客户打包分发时 exe 目录名是中文是常态，这个坑必须在代码层面堵死而不是要求客户改目录名。

修复后实测（2026-07-02 晚，视频发布，单账号微信-1）：**全流程走通**——朋友圈按钮识别、朋友圈弹窗、相机、视频文件选择、文案粘贴、点击发表全部成功，之前"第一步就死"的问题彻底解决。

但同一轮测试暴露出两个新问题：

1. **误报 SUCCESS**：程序点完发表、20 秒内没检测到"未发送"横幅，报了成功；但实际上"视频未发送"横幅出现在**几分钟后**（人工刷朋友圈时才看到）。视频被微信拒发大概率还是账号风控（同一台设备多账号的老问题，测试视频只有 41KB 不存在转码超时）。应对：视频的失败检测窗口从 20s 延长到 75s（检测成本和漏检风险的折中）；**彻底解决需要"发布后回头巡检朋友圈"机制，还没做**——20s/75s 的窗口本质都是赌横幅出现得够早。

## 修复：启动时检测微信窗口会把最后一个微信窗口留在最前面

现象：打开 exe 后，程序自己的窗口没有出现在最前面，反而是被检测流程最后激活的那个微信窗口挡在最前。

根因（`window_manager.py` 的 `find_wechat_windows()`）：检测每个微信账号是否登录时要读头像，读头像必须先 `activate_window()` 把对应微信窗口激活到前台（硬件加速渲染的区域不可见状态截不出来）。检测完所有账号后，函数原本想恢复到"检测前的前台窗口"：

```python
foreground_hwnd = user32.GetForegroundWindow()   # 这里拿到的窗口
...                                                # 中间挨个激活微信窗口
user32.SetForegroundWindow(foreground_hwnd)       # 想恢复，但两个问题：
```

问题①：`foreground_hwnd` 是在 `find_wechat_windows()` 调用时（`main.py` 的 `_launch_main()` 里，MainWindow 还没构造）抓的，那时程序自己的窗口根本还不存在，恢复目标从一开始就不是"我们自己的程序"。
问题②：恢复用的是裸 `SetForegroundWindow`，不像 `activate_window()` 那样用 `AttachThreadInput` 技巧借前台线程的焦点权限——调用方不是当前前台进程时，这种裸调用经常被 Windows 焦点锁定机制直接拒绝，静默失败。

两个问题叠加，效果就是：恢复没有生效，最后一个被 `activate_window()` 激活的微信窗口就留在了最前面。

最初的修复：`MainWindow.run()` 里，窗口构造完成、`mainloop()` 之前，主动用跟 `activate_window()` 同款的 `AttachThreadInput` 抢焦点逻辑对自己的窗口抢一次前台。**这个版本引入了一个更严重的新 bug**：`AttachThreadInput` 会临时把当前线程的输入队列跟目标线程（通常是刚才被激活的微信线程）接在一起，即使正确 detach，也会让 Windows 内部的焦点/前台追踪状态留下副作用——实测发现，这样抢完前台之后，"选文件夹"/"选文件"按钮点了完全没反应，`tkinter.filedialog.askdirectory`/`askopenfilenames` 弹不出对话框，而且不报错、不抛异常（Windows shell 原生文件选择对话框自己也要走一套前台激活逻辑，被弄脏的线程输入队列状态跟它冲突）。

排查方法：写最小复现脚本——先验证裸 `tkinter.filedialog.askdirectory` 单独调用正常；再验证只 `import window_manager`（触发 win32gui/win32ui 相关代码）不影响对话框；最后验证"先调用 `activate_window(root.winfo_id())` 再点按钮开对话框"——第三步稳定复现"点了没反应"，实锤问题出在 `AttachThreadInput` 这个动作本身，不是 win32 依赖或别的什么原因。

最终修复：改用纯 Tkinter 层面的技巧，不再碰 `AttachThreadInput`：

```python
def run(self):
    self.root.lift()
    self.root.attributes("-topmost", True)
    self.root.after(150, lambda: self.root.attributes("-topmost", False))
    self.root.focus_force()
    self.root.mainloop()
```

`-topmost` 短暂置顶再取消、`focus_force()` 强制抢焦点，都是 Tk 自己的窗口管理 API，不涉及底层线程输入队列操作，重新验证过不会影响文件选择对话框。这个版本还没有实测验证启动抢焦点本身是否有效（弹出对话框不受影响这点已验证）。

## 调研：客户反馈的两条风控信息查证 + 客户真实场景

2026-07-02 客户反馈两条信息，查证结论：**都属实**。

1. **换网络环境会触发安全提示/封号**：微信官方提示语里就有"因使用行为或设备网络环境异常"这一类；公开资料确认的诱因包括 IP 异常变动、异地登录、频繁切换设备/网络。私域运营圈实操口径：异地/换设备后需要 1-3 天"过渡期"再恢复高频操作；同网络下有被风控的账号会被连带（连过问题 WiFi 也算）。
2. **临近春节查得严**：月初、月底、重大节点人工审核收紧；行业统计 11 月至次年 1 月被封/被限的营销号超 10 万个。另注意 2026-04-29 生效的新版《微信个人账号使用规范》给了更明确的处置依据。

对本项目的含义：风控不只看操作行为，还看**环境稳定性**——这解释了为什么同样的自动化操作有时成功有时被拒发。给客户的使用建议应包含：固定网络环境、换环境后过渡 1-3 天再自动发布、春节前（约 11 月-次年 1 月）主动降频、新登录账号头几天不用工具。

**客户真实场景（重要背景）**：客户目前用 **20 部手机登 20 个微信号**人工发朋友圈，自动化诉求由此而来。这个信息改变了产品方向的权衡：

- 客户用 20 部真机，恰恰是目前**风控隔离最好的形态**（每台设备独立指纹、可各自走 SIM 流量独立 IP）
- 而本项目当前形态（一台 PC 多开微信）已实测确认会触发同设备多账号风控，20 个号搬到一台 PC 上是把隔离优势拆掉，**方向上不成立**
- 更合理的演进：保留 20 部真机的隔离优势，把"自动化"下沉到手机上——PC 只做调度中枢（排班/素材/文案，本项目的 scheduler 养号策略可直接复用），执行层换成 ADB/uiautomator2 驱动真机（一台 PC 通过 USB hub 或 WiFi ADB 控 20 台）。注意事项：各手机走自己的 SIM 流量而非同一个 WiFi（同出口 IP 是关联信号）；各设备排班时间必须独立随机化（群控最容易被抓的特征是多设备行为节奏一致）；iPhone 自动化成本远高于 Android，客户若是 iPhone 需另行评估
- 折中形态（技术成本最低）：PC 端只负责"内容分发"——通过文件传输助手把素材+文案推到各手机，人在手机上完成最后的发表点击。半自动，但把人工中最耗时的部分（内容准备、排班提醒）自动化了，风控暴露面几乎为零
