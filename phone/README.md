# 朋友圈发布助手 · 手机版（ADB 全自动）

PC 通过 ADB 驱动安卓真机，自动完成发朋友圈。配套 20 部真机、20 个微信号的客户场景：
每台手机独立设备指纹、可各走 SIM 流量，**串行**发布（一台发完再下一台），
风控隔离性远好于"一台 PC 多开 20 个微信"（后者已实测会触发风控）。

跟 PC 版（`wechat-moment`）是**两个独立项目**：PC 版一台电脑多开微信、图像识别操作 PC 客户端；
本项目驱动手机真机。调度/养号/重试的**思路**复用 PC 版，执行层完全不同。

---

## 为什么用坐标点击而不是无障碍服务

微信 8.0.52+ 对无障碍服务（AccessibilityService）的界面节点做了**混淆**——脚本读到的元素是
乱的，主流群控框架在微信上平均 14 天失效。所以本项目走**截屏 + 按屏幕比例坐标点击**：
在系统输入层更接近真人，微信不容易封；代价是依赖 UI 布局稳定（客户确认发圈按钮位置不会变）。

坐标全部用**屏幕比例（0~1）**表达，不写死像素——UI 不变时天然跨分辨率，不同机型只要布局一致
就通用，不用每台重新标定。

## 环境准备（每台手机一次性配置）

**关键坑：MIUI/HyperOS 上模拟点击默认被锁。** 实测小米15(HyperOS2) 上：

1. 开发者选项 → 打开 **USB调试**
2. 开发者选项 → 打开 **USB调试（安全设置）—— 允许通过USB调试修改权限或模拟点击**
   （这个是模拟点击的开关，普通 USB 调试不够）
3. **打开后必须重启手机**，模拟点击权限才真正生效（不重启会一直报
   `SecurityException: INJECT_EVENTS`）
4. 无线调试：开发者选项 → 无线调试 → 用配对码配对（配对端口和连接端口不同，都要）

> 20 台生产时的取舍：无线调试要连 WiFi，而手机连 WiFi 后微信流量也走 WiFi，与"各走 SIM
> 流量避免同出口 IP"的隔离建议冲突。生产更可能用 USB hub（不占网络，手机继续用 SIM）。
> 测试阶段无线足够。

**PC 端**：需要 Google 官方 platform-tools（adb）。未纳入仓库（体积大），单独下载后
把路径配好即可。

## PC 控制端（2026-07-05 新增）

手机端流程验证通过后，加了一层 PC 控制端——GUI 管任务（素材+文案+设备+排班），
调度器按时间触发，执行层调用 `publisher.publish_moment`。结构仿照 PC 版
`wechat-moment`（`main.py` + `gui/main_window.py` + `scheduler.py`），但账号列表换成
设备列表，执行层是 ADB 驱动真机而不是操作 PC 窗口。**这是完全独立于 PC 版的新程序**，
不共享/不修改 PC 版任何代码（`src/` 目录）。

### 机型坐标 Profile 库

20 台手机型号/分辨率不统一，坐标不能只写一套。`device_profile.py` 按 `ro.product.model`
存一份 Profile（比例坐标 + 图片选择列坐标），运行时落盘在 `device_profiles.json`
（不进仓库，类似 `activation.dat`）。内置种子 Profile 是小米15 那份已实测坐标，
新机型接入前需要**先标定**——目前是开发者用 adb 截屏走一遍流程手动记录坐标（跟这几天
的做法一样），存进 `device_profile.save_profile(model, profile_dict)`；GUI 内置标定向导
是第二期的事，先不做。

### 设备自检（`diagnostics.py`）

新设备接入时跑一遍，逐项确认：ADB连接 / 截屏 / 模拟点击 / **推图片** / **推视频** /
**键盘(ADBKeyboard)**。GUI 里"🔧 设备自检"按钮触发，结果写进运行日志。
推图/视频测试用 PIL/OpenCV 现场生成小的合成测试素材（不依赖仓库外部资源），
测完自动清理设备上的临时文件。

### 激活码

跟 PC 版共用同一套注册码算法（同一个私钥，`auth.py` 逻辑完全复制），但两个程序
`activation.dat` 各自独立——同一个客户注册码两边都能输，各自本地激活各自的程序。

### 已知限制（诚实记录，不是"全自动"的完整闭环）

- 调度触发前，**目标手机需已停在朋友圈页**（自动导航坐标未标定，见上面"待办 3"）
- 失败检测本期未做：`publish_moment` 只要点击流程走完不抛异常就视为"已发布"，
  不检测微信是否真的把内容发出去了（跟 PC 版视频误报是同一类风险，PC 版也没根治）
- 只验证过 1 台设备（小米15），20 台并行管理/USB hub 连接方案未搭建和验证

## 项目结构

```
src/
├── adb.py              ADB 封装（截屏/点击/推图/连接管理，含 MIUI 注入权限识别）
├── auth.py             注册码验证（复制自 PC 版，同私钥）
├── logger.py           日志落盘（复制自 PC 版）
├── device_profile.py   机型坐标 Profile 库（JSON 落盘，内置小米15 种子 Profile）
├── device_manager.py   设备发现 + 机型识别 + 别名分配（含 mDNS 重复设备过滤）
├── distributor.py      素材分发：发布前推图/视频到设备专用文件夹（先清空再推）
├── diagnostics.py      设备自检：连接/截屏/点击/推图/推视频/键盘
├── publisher.py        发圈流程（按机型 Profile 传入坐标，不再是全局硬编码）
├── scheduler.py         调度执行循环（复制自 PC 版，逻辑不变）
├── main.py              入口：授权 → 设备发现 → 主界面 → 调度执行
└── gui/
    ├── activation.py    激活界面（复制自 PC 版）
    └── main_window.py   主界面：设备列表替代账号列表，其余仿 PC 版交互
```

## 防风控：操作节奏随机化

`publisher.py` 各步骤等待都用**随机区间**（`STEP_WAIT`/`PICK_WAIT`/`REVIEW_WAIT`），
不用固定整数秒——固定节奏本身就是机器特征（跟 PC 版一个教训）。尤其**发表前**有个
`REVIEW_WAIT`(2.8~5.6s) 的"看一眼再发"停顿，关键对外动作故意慢下来、更像真人确认。
以后要进一步降风险，可在此基础上加：任务级的随机长间隔（复用 PC 版 scheduler 养号策略）、
每台设备排班独立随机化（多设备行为节奏别一致）。

## 踩坑记录：无线调试下同一台手机在 `adb devices` 里出现两次

`device_manager.py` 开发时发现：无线调试的手机会同时被列出 `ip:port` 和 mDNS 自动
发现的 `adb-xxx._adb-tls-connect._tcp` 两个"设备号"，其实是同一台物理设备——不过滤
会导致设备列表里一台手机显示成两台（别名分配、后续调度都会乱）。修复：过滤掉
`_adb-tls-connect._tcp` 结尾的 mDNS 名字，只保留 `ip:port`/USB 序列号形式。
